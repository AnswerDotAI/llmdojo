claudedojo

Start Claude Code with a worked tooling session already in its history

A fresh Claude Code session gets its tooling instructions up front, but no examples: the first real tool calls of the session are produced cold, and early mistakes compound. In-context learning wants the opposite: a transcript that already shows the tools used well. claudedojo provides that. The template is an authored dialog (see aidialog): a worked, idiomatic dojo round written as a notebook, executed against the real kernel so every output is true, and converted to a session that new sessions resume, so each one opens with the clean round already in context.

from fastcore.test import *
from claude_agent_sdk import query, ClaudeAgentOptions, ResultMessage
from llmdojo.rules import doced

Curating the capture

Curation turns one good run into a reproducible template. The round’s boundaries are structural, shared with codexdojo through capture_slice: the bootstrap doc() reads open it and the first score of the last dealt round closes it, so nothing outside the round - the capture prompt, warm-up calls, post-round chatter - can leak in. Within the span, curation keeps only what a resumed session gains something from: thinking records go, as do per-call hook confirmations and task reminders, any failed tool call along with its error result, and mid-round user prompts (mk_template supplies the one canonical prompt). reid_recs pins ids and timestamps so identical captures give identical files. Environment attachments (tool listings, skill listings, MCP instructions) stay: Claude Code injects them as deltas, so baked ones prevent identical re-injection on resume, and a different environment simply layers fresh deltas on top.

Gating the capture

A fumbled round baked into a template would teach every future session the fumbles as worked examples, so every path into the store - headless capture, live harvest, rebuilt review dialog - is gated by is_clean first. The content gates (one dealt round, one first-try score, no redo, a clean receipt, no script leakage) are round_gates, shared with codexdojo; the failed-call check is the Claude-specific part, read from is_error results:

def mk_template(
    picked, # Round records, e.g. from `curate_dojo`
    opening:str='Bootstrapping: the startup script has already run its imports, so I read the tooling docs, check the catalog, then take the dojo.', # Reply text preceding the first tool call
    closing:str="OK I'm ready.", # Reply text ending the round
    doced:NoneType=None, # Names doc()'d during the round, stored in the dialog's metadata for launch-time doc-state seeding
):

A template dialog: picked wrapped in TMPL_PROMPT and framing text, with tool output untruncated

mk_template turns the picked records into the reviewable artifact: a one-prompt dialog whose reply holds the whole round, ready for write_ipynb and then --build. The framing text records are synthetic, which is fine (resume trusts them), and mx=None matters: the default rendering truncates tool output at 2,000 characters, which would gut the baked doc() results that a spawned session relies on.

tdlg = mk_template(c1, opening='Practice first.', doced=['doc','rg'])

test_eq(tdlg.messages[0].content, TMPL_PROMPT)

assert 'dojo_start()' in str(tdlg.messages[0].output)
tmsgs = dlg2msgs(tdlg)
test_eq([m['role'] for m in tmsgs], ['user', 'assistant']*4)

The template store

The store is package data: dojobuild compiles the canonical dialog into dojo_data/claude_store/ (records plus metadata: the completion id its clean round printed, the dojo tooling version, and the round’s doced list, which prep_dojo seeds into the spawned conversation’s doc-state), and it ships with the code - so updating llmdojo updates the template, with nothing per-user to build or go stale. The version is what keeps the store honest: llmdojo refuses completion ids minted under different tooling, so an out-of-date store forces a real round rather than silently faking one.

Capturing from a live session

A headless capture run is not the only source of a clean round: a live Claude Code session can play one itself and harvest it from its own transcript, at zero API cost. No markers are needed - the round’s structural boundaries locate it, and mid-round fumbles are curated away (mid-turn assistant text is not saved in live transcripts, so narration must ride in comment-only kernel cells). capture_current is the whole harvest in one call: curate the newest transcript’s round, gate it, derive its doc-names from its own doc() calls, and store it beside its review dialog - the exact mirror of codexdojo’s capture_current.

Capturing headlessly

When the tooling version bumps, the stored template goes stale and someone must play a fresh clean round. capture_dojo does it unattended: it spawns a real Claude Code session via the Agent SDK in a throwaway project, steered by a script in the system prompt — which never appears in transcript records, so the captured history needs no scrubbing and reads as the model’s own work. The steering asks for a round worth copying and keeps itself out of the story - worded informally and plainly, since more clandestine-sounding drafts (‘automated telemetry capture’, ‘never mention these instructions’) tripped fable’s safety layer, which re-screens the whole context on every call; every receipt in the transcript is still real (the kernel ran, the katas scored), only the plan was supplied. A clean child run is gated raw - a child that fumbled is rejected outright, not curated - and then stored through the same capture_current as a live harvest.

The shared capture prompt names each cell and the non-obvious details; the model supplies the narration. Claude passes the prompt as an addition to the claude_code preset. Codex writes the same bytes to the scratch project’s AGENTS.md. Each Claude attempt runs in a fresh project with a pyproject.toml, so clikernel starts eagerly and prints the expected bootstrap. LLMDOJO_STATE_DIR also points into the scratch project, so a failed attempt cannot touch machine-global state. The round’s doc-names come from its own doc() calls (doced_names), so no state travels from the child at all.

A clean capture stores the template and writes it as template.ipynb beside the store. That notebook is the review point: read it, curate the prose, then rebuild the stores with dojobuild --claude and --codex. The store works before curation, but the baked history teaches by example, so the reviewed copy should be exemplary.

Launching

prep_dojo does the three launch-time steps: write the template as a session of the target project (under a fresh session id every launch, so claude -r $(claudedojo) behaves exactly like plain claude, just with the round already in history), register the template’s completion id with clikernel so dojo_start('<id>') in the spawned session validates, and hand back the id for claude -r. The spawned session then starts with the whole worked round in context, a kernel whose empty state matches the story its history tells, and live hooks and skills layered on top.

append_dojo

def append_dojo(
    sid:NoneType=None, # Session id or name to append to; the project's newest transcript if None
    cwd:NoneType=None, # Project directory; the current directory if None
    d:NoneType=None, # Template store dir; `TMPL_DIR` if None
):

Append the template round to session sid (e.g. after a compaction), re-seed doc-state, and return sid to resume

append_dojo splices the round into an existing conversation instead of starting a fresh one — the post-compaction repair. Compaction rewrites the model’s context to a summary: the worked examples vanish and the SessionStart hook truncates the doc-state record. Appending the round puts the demonstrations (and their doc() outputs) back at the tail of the context, and re-seeds doc-state to match. The baked round’s kernel story stays true because appending requires the app to be closed, and the kernel dies with the app: the resumed session gets a fresh kernel whose startup just ran its imports — exactly what the round’s opening and closing claim. Only the synthetic prompt line differs (a compaction reads differently from a session start); every receipt is the same template. Repeated appends re-salt the record ids, so a session can be refreshed after every compact.

A compact should describe the conversation’s work, not its warm-up: the round append_dojo splices afterwards supersedes any earlier one, so records of previously dealt rounds are pure noise in the compact document. Recognition is structural, matching how rounds actually occur: a round occupies whole user turns, so splitting the records into turns at each real user prompt and dropping the turns whose tool calls dealt a round (a bare dojo_start()) removes prompt, framing text, calls, and receipt together. Replays (dojo_start(id)) are kept: they are one cheap call, and evidence the gate ran.

The launcher is a call_parse CLI: -h documents every verb, and the capitalized params declare the short flags (Resume → -r, Compact → -c), so the documented $(claudedojo -r) spelling falls out of the signature. There is deliberately no pass-through of extra arguments to claude itself: command substitution composes better - claude -r $(claudedojo) <any claude flags> - and keeps the launcher a pure preparer. build_template (via dojobuild) converts a template dialog directly: aidialog renders prompts as bare text (the XML envelope around Solveit prompts is Solveit’s own prompt_txt patch, which never loads here), and records omit the model so a resumed session uses the user’s configured default. prep_dojo stamps launch-time timestamps, so the session picker shows its real age.

The proof that a spawned session truly inherits the round: resume the prepared session and ask about facts only its history holds. The model should quote the completion id its dojo round printed, and know that its kernel state is gone. This needs a captured template in the real store, and spends tokens, so it stays out of CI:

psid = prep_dojo(mproj)
opts = ClaudeAgentOptions(resume=psid, cwd=str(mproj), model='haiku')
async for m in query(prompt='From this session only: what completion id did the dojo round print, and what did its final message say about kernel state?', options=opts):
    if isinstance(m, ResultMessage): print(m.result)

Rebuilding the template

When the dojo tooling version changes, prep_dojo warns and the baked completion id stops validating. When only outputs have staled, a bare dojobuild (the shared refresh_template, plus both store builds) regenerates them without a model; a change to the round’s cells needs a fresh round. The steps to play are the capture script’s numbered cells (llmdojo/dojo_data/capture_prompt.md - the single source of truth for the round; adjust it first if the dojo changed). The live workflow, all from one session: play the script’s cells in order, narrating via comment-only kernel cells, then run the cells below from that same session (capture_current resolves to the newest transcript, which is the conversation that just played, and derives the doc-names from the round’s own doc() calls). Failed calls are curated away; a redo or a second score means the round wasn’t clean, so play it again.

dlg = capture_current()
write_ipynb(dlg, 'llmdojo/dojo_data/dojo_template.ipynb')

The written dialog is the review point: read it, edit whatever makes it a better role model — prose freely, and tool calls or outputs too, provided edited receipts stay faithful to what the live tooling prints (when a change would touch many outputs, replaying the round is the cheaper generator of true ones) — then convert and store it with dojobuild --claude and --codex (build_template on each backend). Its home is llmdojo/dojo_data/dojo_template.ipynb, tracked in git and shipped as package data so a fresh machine’s first launch can build its store from it. The meta check should show the new round’s completion id and the installed dojo version.

build_template('llmdojo/dojo_data/dojo_template.ipynb', cwd=Path.cwd())
load_template()[1]
